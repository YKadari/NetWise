# Batch 9: guided rental advisor

## Question to evaluator mapping

The guided path submits the existing `RentalOffer` and optional `FinancialProfile` to `POST /api/rental/evaluate`. It performs no financial calculation in React. The mapping was reviewed against `backend/app/rental/models.py` and `backend/app/rental/calculations.py` before implementation.

| Guided answer | Existing request field | Rule |
|---|---|---|
| Advertised rent, lease length | `monthly_base_rent`, `lease_term_months` | Positive cents-accurate amount; 1–120 whole months. |
| Sharing and expected roommate payment | `expected_roommate_contribution` | User enters the **roommate contribution**, never an assumed equal split. Alone is confirmed `none`; uncertain sharing is `unknown`. Household rent remains the full advertised rent. |
| Refundable security deposit | `upfront.security_deposit` | `provided` amount is refundable cash held, not rent expense. Explicit no is `none`; uncertainty is `unknown`. Nonrefundable charges belong in `nonrefundable_fees`. An unclear refund policy stays unknown. |
| First and last rent paid before move-in | `upfront.first_month_rent_due_upfront`, `last_month_rent_due_upfront` | Yes/no/unknown. Backend allocates prepayment to the corresponding month rather than adding rent expense. |
| Known application, administration, other nonrefundable fees | `upfront.nonrefundable_fees` and `_status` | Listed positive charges count as expenses. Any unconfirmed fee list leaves status `unknown`; explicit complete list uses `complete`. |
| Other refundable upfront charge | `upfront.other_charges` and `_status` | Only explicitly refundable charges are marked refundable. Otherwise the charge remains unknown until treatment is clarified. |
| Holding deposit | `upfront.holding_deposit` and `_status` | A known payment is submitted only with its exact credit/refund treatment. Otherwise `unknown`; explicit absence is `none`. |
| Mandatory monthly fees, internet, parking | `recurring_charges` and `_status` | Only confirmed required amounts enter the list. Optional costs do not enter contractual totals; any unanswered required-charge question keeps status `unknown`. Included services are not duplicated. |
| Utilities | `utilities` | Included, estimated with a stated amount, or unknown. Estimate is not a guaranteed bill. |
| Discount | `concessions` | Only stated free-rent month or credit with month and amount; no guessed discount. |
| Optional take-home pay, savings, essentials, reserve | `FinancialProfile` | Submitted only when the user opts in. No stored profile. Backend determines affordability and cash flow. |

The existing stress endpoint continues to receive the same offer and optional profile. Unknown monetary terms are never sent as zero. The API cannot model an upfront charge with known amount but unclear refundable treatment precisely; the guided path keeps that category unknown and asks the renter to clarify it.

## Journey and adaptive behavior

Analyze now leads with **Start guided analysis**. Four stages ask about the rental, move-in cash, monthly charges, and optional financial readiness. Back keeps answers in memory. Sharing, deposit, fee, parking, utility, and discount controls reveal amount fields only when relevant. Changing an answer hides and excludes its dependent amount on submission. A detailed manual form remains available for terms beyond the guided questions. Compare and stress tests continue to use the same saved `RentalOffer` and backend endpoints.

The sample opens the guided questions with explicitly synthetic answers. It uses a $1,600 monthly rent, 12 months, an $800 refundable deposit, a $100 application fee, $40 required internet, $130 estimated utilities, and first-month rent paid before move-in. Administration fees, other required monthly charges, discounts, and a holding deposit remain unknown. The sample invokes the existing evaluator only after the visitor finishes the four stages. The evaluator returned **$1,770 known monthly housing**, **$2,500 known upfront cash**, **$21,340 known nonrefundable lease expense**, and **$800 refundable cash held**. Monthly, upfront, and lease totals were all flagged incomplete. Prepaid first-month rent appears in move-in cash and is allocated to month one rather than added to lease expense. The financial result, not React, determines all amounts.

Results retain the existing four financial metrics, completeness labels, cash-flow detail, comparison actions, optional profile editing, and stress tests. A separate **Questions to ask before signing** list is generated by fixed frontend rules from unanswered guided terms. It asks about fee schedules, refund treatment, prepaid rent timing, services, discounts, roommate contributions, and early departure. These are verification prompts, not inferred lease facts.

## Optional AI and privacy

The Analyze AI path accepts pasted text and retains the extraction draft, evidence, and explicit human review before confirmation. The PDF upload control is hidden in Analyze for this release; its backend route and existing component logic are retained. In guided stages two and three, a small clause helper uses the same text extraction API when `/api/lease/status` says it is ready. It shows source excerpts and ambiguity; it **never writes candidates into guided answers**. When unavailable, it offers deterministic advice to keep the answer uncertain and ask for clarification. This is a term-finding aid, not a general chatbot or a legal interpretation. The existing extraction API does not provide a separate plain-English clause paraphrase, so that part of the desired helper remains deferred.

Financial readiness is optional. When selected, the four supported values are submitted to the backend evaluator for that request; the frontend does not persist them in browser storage. Lease text submitted to AI is sent through the backend to Google Gemini. Public Gemini extraction remains disabled by `render.yaml`.

The interface uses labeled native inputs, radio groups, visible focus outlines, text progress, large buttons, and responsive card grids. Unknown is never converted to confirmed zero. The backend's `recurring_charges_status`, `utilities.status`, `security_deposit.status`, and upfront completeness fields carry uncertainty into results. Some uncertainty, such as unknown concession terms, cannot be represented as a backend completeness flag; the question list calls it out separately.
